# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DP LMW (internal package name still `memory-vault`): a photo/video storage system with manual and automatic album grouping (by capture date / GPS proximity). npm workspaces monorepo with a hard separation between frontend, backend, and AI/grouping logic.

## Commands

```
npm install                                    # installs all workspaces
npm run build -w ai -w packages/shared          # build internal packages (do this before running be/)
npm run -w be prisma:generate                   # regenerate Prisma client after schema.prisma changes — see warning below
npm run -w be prisma:migrate                    # create/apply a migration (interactive — see Database section if it refuses)
npm run -w be prisma:seed                       # populate 4 sample photos across 2 date clusters (skips if seed data already present)
npm run -w be prisma:studio                     # inspect the DB
npm run dev:be                                  # backend on :4000 (tsx watch)
npm run dev:fe                                  # frontend on :3000 (next dev)
npm run build                                   # ai -> shared -> prisma generate -> be -> fe, in that order
```

**`prisma generate` is not optional and npm doesn't run it for you.** `be`'s TypeScript code (`be/src/routes/*.ts`) relies on Prisma's *generated* types (`db.album.findUnique(...)` returning a properly-shaped `Album & { media: ... }`, not `any`). On a machine/CI environment that has never run it, `@prisma/client` is an unusable stub and `tsc` fails with things like `Parameter 'am' implicitly has an 'any' type` or `Property 'thumbnailKey' does not exist on type 'MediaPoint'` — this is exactly what happened on the first Render deploy, whose `buildCommand` built `be` without generating first; fixed by adding `npm run -w be prisma:generate` into both `render.yaml`'s `buildCommand` and the root `package.json`'s `build` script, ahead of `npm run build -w be`. `npm install` alone does not reliably trigger it in this workspace layout — don't assume a fresh environment has a working Prisma Client just because dependencies installed cleanly.

No test suite exists yet. There is no root lint/typecheck script — `ai` and `packages/shared` each expose `typecheck`/`build` via `tsc`; `fe` has `npm run -w fe lint` (eslint-config-next).

Env files: copy `be/.env.example` -> `be/.env` and `fe/.env.example` -> `fe/.env` (both already exist locally with working dev values — don't overwrite blindly). `be` needs `DATABASE_URL`, `STORAGE_*` (S3-compatible), `ADMIN_PASSWORD`, `JWT_SECRET`, `FRONTEND_ORIGIN`. `fe` needs only `NEXT_PUBLIC_API_URL`. `be/src/server.ts` loads `.env` via a top-of-file `import "dotenv/config"` — Prisma reads `DATABASE_URL` itself regardless, which can mask a missing/broken `.env` (DB calls work, but `ADMIN_PASSWORD`/`JWT_SECRET`/`STORAGE_*` silently come back `undefined`, e.g. admin login 401s with no other symptom). If `fe` can't reach `be`, check `fe/.env`'s `NEXT_PUBLIC_API_URL` is set and `fe`'s dev server was restarted after any env change — Next.js only reads `NEXT_PUBLIC_*` vars at server start.

## Database

**Where it physically lives**: **Supabase** (cloud), project ref `tokosunpcsrcgqjjdwwz`, region `ap-southeast-1`. This is the real, shared, always-on database — anyone the app is deployed for reads/writes the same data, not a per-machine copy. `be/.env`'s `DATABASE_URL` is Supabase's session-mode pooler connection string (`postgresql://postgres.tokosunpcsrcgqjjdwwz:...@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres`) — session mode (port 5432 on the pooler host), not the transaction-mode pooler, because `be/` is a persistent Node process and Prisma needs prepared-statement support that transaction mode doesn't give. A local PostgreSQL 16 Windows service was used earlier in development (data dir `C:\Program Files\PostgreSQL\16\data`, db name `memoryvault`) — that data was intentionally discarded, not migrated, when moving to Supabase, so don't go looking for it as a source of truth.

**Schema** (`be/prisma/schema.prisma`): `Media`, `Album`, `AlbumMedia` (join table), two enums (`MediaType`, `AlbumSource`). No `User` table — see Auth model below. Constraints worth knowing when changing this file:
- `Media.storageKey` is `@unique` — it's the object-storage key, so a duplicate would mean two rows silently pointing at the same file.
- Indexes exist specifically for the query patterns in `be/src/routes/`: `Media(uploadedAt)` and `Album(createdAt)` back the two list endpoints' `orderBy`, `Media(takenAt)` backs `groupByDate`'s sort, `AlbumMedia(mediaId)` backs the `albums: { none: {} }` "ungrouped media" filter in `/auto-generate`. If you add a new sort/filter to a list route, check whether it needs a matching index rather than assuming one exists.
- Migrations are committed under `be/prisma/migrations/` (tracked in git, not gitignored) — `20260804161130_init` (initial schema), `20260804170000_add_indexes_and_constraints`, then `20260805040307_add_soft_delete` (nullable `deletedAt` on `Media`/`Album` — see Trash below), all applied to Supabase via `prisma migrate deploy` (the nullable-column one ran fine non-interactively; earlier ones with data-loss-risk changes needed the manual-SQL workaround). `prisma migrate dev` is interactive and will refuse to run in a non-interactive shell/agent session when it needs to show a data-loss warning (e.g. adding a `@unique` constraint) — in that situation generate the SQL by hand instead (`prisma migrate diff --from-migrations ./prisma/migrations --to-schema-datamodel ./prisma/schema.prisma --shadow-database-url <a scratch db> --script`), write it into a new timestamped folder under `migrations/`, then apply with `prisma migrate deploy` (non-interactive-safe, just applies pending migration folders).
- `be/prisma/seed.ts` (run via `npm run -w be prisma:seed`, wired through Prisma's `"prisma": {"seed": ...}` field in `be/package.json`) generates 4 real JPEGs and pushes them through `be/src/lib/storage.ts`'s `uploadObject` (so they land wherever `STORAGE_DRIVER` currently points — Supabase Storage or local disk), inserting matching `Media` rows across two `takenAt` clusters. Idempotent — skips if a `media/seed-*` row already exists.

**Backup**: Supabase takes its own automated backups (see the project's Database → Backups dashboard tab) — that's the primary story now, not manual `pg_dump`. For an ad-hoc manual dump against the cloud DB: `pg_dump` needs its options before the connection target:
```
"C:\Program Files\PostgreSQL\16\bin\pg_dump.exe" "postgresql://postgres.tokosunpcsrcgqjjdwwz:<password>@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres" -Fc -f backup.dump
```
A DB-only backup is incomplete when `STORAGE_DRIVER=local`: `Media.storageKey` rows would point at files in `be/uploads/` that a DB dump doesn't capture. Under the current `STORAGE_DRIVER=s3` (Supabase Storage), the bucket itself is the durable copy of file bytes, so a Postgres backup alone is sufficient for the metadata.

## Auth model — read this before touching routes

This is a **shared public vault, not a multi-user app**. There are no user accounts. Viewing, uploading, and editing (rename album, add/remove items, run auto-generate) are open to anyone with the URL — no token required. The **only** login is a single shared admin password (`ADMIN_PASSWORD`), and it gates everything destructive/admin-only: `DELETE /api/media/:id`, `DELETE /api/albums/:id` (both soft-delete, see Trash below), `POST /:id/restore`, `DELETE /:id/permanent`, and the `GET /trash/list` / `GET /:id/trash-url` read endpoints — all behind `be/src/middleware/requireAdmin.ts`. There is no per-resource `ownerId` anywhere in the schema or DTOs — don't reintroduce one without an explicit reason to.

When adding a new route, default to public. Only wrap it in `requireAdmin` if it's destructive or trash-related, matching the existing routes.

### Confirmation dialogs — never use window.confirm()
`fe/src/components/ui/ConfirmDialogProvider.tsx` is mounted once in `layout.tsx` and exposes `useConfirm()` — an async `confirm({ title, description?, confirmLabel?, cancelLabel?, danger? }) => Promise<boolean>` that renders an on-brand modal instead of the browser's native dialog. All four destructive actions (media delete, album delete, trash permanent-delete ×2) use it; the two soft-deletes word their `description` as recoverable ("Chuyển vào thùng rác — có thể khôi phục lại sau"), the two permanent-deletes as truly final ("Không thể hoàn tác") — keep that distinction if you add another confirm call. `danger: true` renders the confirm button in `danger` red; omit it for non-destructive confirmations.

### Trash — deletes are soft by default
`DELETE /api/media/:id` and `DELETE /api/albums/:id` don't actually remove anything anymore — they set `deletedAt` and the item disappears from every public surface (list endpoints, album detail's nested media, `/auto-generate`'s ungrouped-media query, and the signed-URL endpoints, which 404 for a trashed item's id) while staying in Postgres/storage. Two more admin routes complete the loop: `POST /api/{media,albums}/:id/restore` (clears `deletedAt`) and `DELETE /api/{media,albums}/:id/permanent` (the actual hard delete — removes the storage object(s) and the DB row, same logic the old plain `DELETE` used to have). Admins browse the trash at `fe/src/app/trash/page.tsx` (client-side admin-token gated, same pattern as other admin actions) via `GET /api/media/trash/list` / `GET /api/albums/trash/list`; thumbnails there come from `GET /api/media/:id/trash-url` (admin-only — a separate endpoint from the public `/:id/url`, which deliberately keeps 404ing trashed items so a trashed item's signed URL can never leak to a non-admin who happens to have its id).

**If you add a new read query anywhere in `be/src/routes/`, filter `deletedAt: null` (or, for `AlbumMedia`-nested media, `media: { deletedAt: null }`)** — nothing does this automatically; it was a real bug already (an unmoderated upload sat fully public because the first version of a "list all media" page had no soft-delete to lean on at all, before this system existed).

## Architecture

Four workspaces, each with a distinct responsibility. Reading only one is usually not enough to change a feature end-to-end — a new field on `Media`, for example, touches `be/prisma/schema.prisma`, `packages/shared` (DTO), the `be` route that maps Prisma rows to DTOs, and the `fe` component that renders it.

- **`fe/`** — Next.js App Router, UI only. It holds no server-side data logic: every page that needs data is a **client component** (`"use client"`) that calls `be/` over HTTP via `fe/src/lib/api-client.ts`. There is no Next.js `api/` folder in `fe/` — that's deliberate, all API logic lives in `be/`.
  - Admin login: `fe/src/app/admin-login/page.tsx` is a plain password form that POSTs to `be`'s `/api/auth/admin-login` and stores the returned JWT via `fe/src/lib/session.ts` (localStorage key `mv_admin_token`). `api-client.ts` attaches it as a `Bearer` header on every request, but the backend only checks it on the two delete routes — its presence elsewhere is a no-op.
  - Delete buttons (`MediaCard.tsx`, `AlbumCard.tsx`) check `getSessionToken()` client-side before calling delete; if absent they redirect to `/admin-login?next=<current path>` instead of letting the request 401. Same pattern for `fe/src/app/trash/page.tsx` (admin-only trash browser — redirects on mount if no token).
  - `fe/src/app/media/page.tsx` ("Ảnh & Video" in the nav) lists every non-trashed `Media` row via `GET /api/media` — this didn't exist for a while, meaning uploads had nowhere to be seen outside an album; don't let that regress. `UploadDropzone.tsx` shows a local object-URL preview + per-file status the moment files are picked (before the network request resolves), then a result banner once the whole batch settles, linking to `/media`.
- **`be/`** — Express + Prisma REST API (`be/src/server.ts`). Not deployable as a serverless function (uses `multer` in-memory uploads + `sharp`/exif processing) — needs a long-running Node process.
  - `be/src/routes/{auth,media,albums}.ts` are the HTTP layer: parse request, call Prisma (`be/src/lib/db.ts`) and/or `@memory-vault/ai`, map results to `@memory-vault/shared` DTOs, respond. Routes own all persistence — `ai/` never touches the database.
  - **Every async route handler must be wrapped in `be/src/lib/asyncHandler.ts`.** Express 4 doesn't catch a rejected promise thrown inside an `async (req, res) => {...}` handler — it becomes an unhandled rejection and crashes the whole Node process (hit for real: a transient network blip reaching Supabase took down the entire local dev server, not just one request). `asyncHandler` forwards the error to `server.ts`'s catch-all error middleware instead, which returns 500 and keeps the process alive. `auth.ts`'s handler is sync with no DB call, so it's the one exception that doesn't need wrapping.
  - `be/prisma/schema.prisma` — models: `Media` (has `storageKey`/`thumbnailKey` pointing into object storage, plus EXIF-derived `takenAt`/`latitude`/`longitude`), `Album` (`source`: `MANUAL` | `AUTO_DATE` | `AUTO_LOCATION`), and the `AlbumMedia` join table. No `User` model.
- **`ai/`** (`@memory-vault/ai`) — the "smart" logic, intentionally decoupled from Prisma/the database so it stays pure and testable in isolation:
  - `grouping.ts` — `groupByDate`/`groupByLocation`: pure functions over plain `{ id, takenAt, latitude, longitude }` points, no I/O. `be/src/routes/albums.ts` fetches ungrouped `Media` rows, calls these, then persists the resulting groups as `Album` rows itself.
  - `exif.ts` / `thumbnail.ts` — EXIF extraction and thumbnail generation, invoked from `be/src/routes/media.ts` during upload.
  - `tagging.ts` — placeholder for future LLM-based captioning/album-title suggestions; not wired up.
  - `video.ts` — placeholder for turning an album into a slideshow/video (ffmpeg-based). `be`'s `POST /api/albums/:id/video` calls it and returns 501 until it's implemented — that's the "tạo video" feature, deliberately stubbed rather than half-built.
- **`packages/shared`** (`@memory-vault/shared`) — the API contract: `MediaDTO`/`AlbumDTO`/`AlbumDetailDTO` types imported by both `fe` and `be` so their view of a resource can't silently drift apart. Dates cross the wire as ISO strings, not `Date` objects.

### Media display flow
Object storage is private; nothing is served by public URL. List/detail endpoints return DTOs with `thumbnailUrl: null`, and `fe/src/components/media/MediaCard.tsx` separately calls `GET /api/media/:id/url` to fetch a short-lived signed URL per item. Don't try to shortcut this by adding public bucket URLs to the DTO. Pass `?original=1` on that same endpoint to get the full-size `storageKey` instead of `thumbnailKey` — `MediaLightbox.tsx` uses this for its detail view; grid thumbnails don't.

### "Recently viewed" is client-side only, no server concept of it
`fe/src/lib/recentlyViewed.ts` records a `(kind, id, viewedAt)` entry to `localStorage` whenever `MediaLightbox` opens an item or an album detail page loads — there's no accounts, so "recently viewed" can only ever mean "on this browser." The home page (`fe/src/app/page.tsx`) reads those ids back, cross-references them against the full `GET /api/media` / `GET /api/albums` lists (no per-id fetch endpoint exists, so this is a client-side join, fine at this app's scale), and renders "Album xem gần đây" / "Ảnh & video xem gần đây" sections — both omitted entirely on a browser with no view history yet, rather than showing an empty state.

Clicking a `MediaCard` opens `MediaLightbox.tsx` (full-size image/video, metadata, prev/next, Escape/backdrop/✕ to close) — `MediaGrid.tsx` owns the open/index state and is shared by both `/media` and album detail pages, so the lightbox works in both automatically. `fe/src/app/media/page.tsx` also has a Tất cả/Ảnh/Video filter (client-side, filters the already-fetched list by `type` — no new backend query param).

### Album CRUD
Full create/read/update/delete has existed on `be/src/routes/albums.ts` since the start; `fe/` was missing UI for everything except read/delete for a while — now complete: `CreateAlbumDialog.tsx` (title+description, no media picker at creation time — add media afterward) wired from the "+ Album mới" button on `/albums`; inline rename (pencil icon next to the `<h1>`) on the album detail page calling `PATCH /api/albums/:id`; `AddMediaDialog.tsx` (checkbox picker over `GET /api/media`, excluding what's already in the album) for adding items via `addMediaIds`. Removing an item from an album (`removeMediaIds`) is a *different* action from deleting the media itself — `MediaCard` takes an optional `onRemoveFromAlbum` prop (only passed by the album detail page, via `MediaGrid`) rendering a second button distinct from the delete "×"; don't conflate the two or a "gỡ khỏi album" click will end up soft-deleting the media everywhere instead of just detaching it from that one album.

### Back navigation and album search
`fe/src/components/ui/BackButton.tsx` is a small shared "Quay lại" control (`router.back()`, falling back to `router.push(fallbackHref)` — default `/` — when `window.history.length <= 1`, i.e. a bookmarked/shared link with no in-app history) mounted at the top of `/upload`, `/media`, `/albums`, `/albums/[id]` (passes `fallbackHref="/albums"` specifically, since coming from a share link should land on the albums list, not home), `/admin-login`, and `/trash`. Use it rather than a one-off `<Link href="...">` on any future page that's reachable from more than one place, so "back" always means "wherever I actually came from."

`/albums` also has a client-side search box (magnifying-glass icon, filters the already-fetched `AlbumDTO[]` by `title.toLowerCase().includes(query)` via `useMemo`, no backend query param — consistent with the `/media` type filter) showing a "Không tìm thấy album nào khớp với ..." message when the query matches nothing.

### Storage driver: local vs s3
`be/src/lib/storage.ts` supports two drivers selected by `STORAGE_DRIVER`: `"local"` (writes to `be/uploads/`, served unsigned via `app.use("/files", express.static(...))` in `server.ts`, zero cloud setup — useful if working offline or Supabase is unreachable) and `"s3"` (real signed URLs, **this is what's actually configured right now**). `STORAGE_DRIVER=s3` currently points at **Supabase Storage**'s S3-compatible endpoint, not Cloudflare R2 — despite `storage.ts`'s comments mentioning R2 as an example, the live values in `be/.env` are:
```
STORAGE_BUCKET="DPLMW"
STORAGE_REGION="ap-southeast-1"
STORAGE_ENDPOINT="https://tokosunpcsrcgqjjdwwz.supabase.co/storage/v1/s3"
```
The `S3Client` is constructed with `forcePathStyle: true` in `storage.ts` — required for Supabase Storage's endpoint (path-style `endpoint/bucket/key`, not virtual-hosted-style `bucket.endpoint/key`); harmless if this is ever pointed at R2 instead, which supports both styles. **Never ship `local` to production** — it has no real URL expiry and no auth on the static route. The `/files` static route in `server.ts` auto-disables itself whenever `STORAGE_DRIVER=s3`.

### Auto-grouping needs a takenAt fallback
`ai/src/grouping.ts`'s `groupByDate` filters out any media whose `takenAt` is null before sorting — EXIF-less uploads (screenshots, re-saved/re-exported images) would otherwise never join an album. `be/src/routes/albums.ts`'s `/auto-generate` handler works around this by mapping `takenAt: m.takenAt ?? m.uploadedAt` before calling `groupByDate`. If you add another caller of `groupByDate`/`groupByLocation`, apply the same fallback there — it's not baked into the `ai/` functions themselves (they stay pure/unopinionated about fallback policy).

## Design system

Brand: **DP LMW**, blue/white with warm-orange and teal accents for variety (not monochrome blue). Tokens live as CSS custom properties in `fe/src/app/globals.css` (`:root` for light, `@media (prefers-color-scheme: dark)` for dark — no manual theme toggle exists yet, so there's no `[data-theme]` override block; add one if a toggle is ever built) and are exposed to Tailwind via `fe/tailwind.config.ts` (`bg`, `surface`, `surface2`, `border`, `ink`, `ink-muted`, `ink-faint`, `accent`/`accent-strong`/`accent-soft`, `secondary`/`secondary-soft`, `tertiary`/`tertiary-soft`, `danger`, `success`). Use these tokens (`bg-accent`, `text-ink-muted`, etc.) rather than raw Tailwind grays/blues — `neutral-*`/`blue-*` classes from the original scaffold have all been replaced. `secondary` (warm orange) marks `AUTO_DATE`/`AUTO_LOCATION` album source dots (`accent` blue marks `MANUAL`) — kept distinct from `success`/`danger` since those are semantic (result of an action), not decorative. `tertiary` (teal) is used for the "view albums" home-page icon accent, purely for visual variety. First palette (shipped, then revised): background/text read as too dark/heavy — lightened `bg`/`surface-2`/`border` and softened `ink` from near-black navy (#0f2036) to a lighter slate (#2c3a53), and brightened `accent` from a deep cobalt (#1b4ca8) to a friendlier sky-blue (#3d7fe0).

Typography: three `next/font/google` faces wired in `fe/src/app/layout.tsx` — **Merriweather** (serif, `font-display`, weights 700/900 only — it has no 500/600, unlike the Fraunces it replaced) for the wordmark and page `<h1>`s/headings only, **Open Sans** (`font-sans`, the body default) for everything else, **IBM Plex Mono** (`font-mono`) for counts/dates/tabular data, unchanged. This is the current standing choice — apply it to any new heading/body text going forward rather than reaching for another face (previously Fraunces/Public Sans; before that, don't reintroduce Inter/Space Grotesk either).

Layout: `fe/src/components/layout/TopBar.tsx` renders the brand mark + wordmark, the pill-style nav, and the admin-status pill, and is mounted once in `layout.tsx` — page components should not duplicate navigation. A full HTML mockup of all four screens (home, upload, albums, album detail) was used to derive these tokens; it's not part of the repo, just the design reference the current components were built from.

The brand mark is the "DP" lettermark (`font-display`, white on the accent gradient square) inline in `TopBar.tsx`, duplicated by hand as `<text>` in `fe/src/app/icon.svg` (Next.js App Router auto-serves `app/icon.svg` as the favicon — confirmed at `/icon.svg` after a production build) since Next's icon route can't import a React component — if the TopBar mark ever changes, update `icon.svg` to match. A wordless "stacked photos" glyph (two overlapping colored squares) was tried and reverted back to the lettermark by request; an earlier proposed logo (a modified Domino's Pizza mark) was declined outright and never implemented — don't reintroduce a real company's trademark here.

**Mobile/responsive is load-bearing, not an afterthought** — verified at iPhone-width viewport with no horizontal overflow on any page. Two patterns to preserve when touching layout:
- `TopBar.tsx`: the nav pill wraps to its own full-width row below the brand/admin row on narrow screens (`order-3 w-full ... sm:order-none sm:w-auto`), and the admin-status label text is `hidden sm:inline` (only the colored dot shows on mobile, wrapped in a `title` attribute for a11y).
- Delete buttons (`MediaCard.tsx`, `AlbumCard.tsx`): they're `opacity-80` by default and only drop to `opacity-0`/hover-reveal at `md:` and up (`md:opacity-0 md:group-hover:opacity-100`). Don't go back to a plain `opacity-0 group-hover:opacity-100` — touch devices have no hover state, so that would make delete unreachable on mobile.

### Deploy target — live, not hypothetical

This is actually deployed, not just planned:
- **`fe/`** → Vercel, https://dp-lmw-fe.vercel.app (repo root directory set to `fe` in Vercel project settings). `NEXT_PUBLIC_API_URL` env var points at the Render backend.
- **`be/`** → Render free web service, https://dp-lmw-be.onrender.com, deployed via the `render.yaml` Blueprint at repo root. `FRONTEND_ORIGIN` env var points at the Vercel URL above (must match exactly or CORS blocks every request from `fe/`). Free tier spins down after 15 min idle — first request after that takes ~30-50s.
  - **Auto-Deploy has silently failed to trigger multiple times even with the service's "Auto-Deploy: On Commit" setting correctly enabled** — not a config problem, the GitHub→Render webhook has just not fired on some pushes. After any `be/` change, don't assume it's live: verify with something that only the new code would produce (e.g. hit a new/changed endpoint and check the actual response shape — a plain `/health` 200 proves nothing, since Render keeps the old instance serving until a new deploy actually completes). If it's stale, go to the Render dashboard and **Manual Deploy → Deploy latest commit** on the `dp-lmw-be` service.
- **DB** → Supabase Postgres, **Storage** → Supabase Storage (see Database section above).
- GitHub: https://github.com/Absinthe-Gin/dp-lmw, `main` branch. Both Vercel and Render auto-deploy on push — Vercel picks up `render.yaml`... no, Vercel doesn't touch `render.yaml`; Vercel redeploys `fe/` on every push automatically, Render's Blueprint service does too, but **only for `startCommand`/env execution** — if you change `render.yaml`'s `buildCommand` itself, a plain push is not guaranteed to update the already-created service's stored build command; go to the Render dashboard's Blueprint page and click **Manual Sync**, or edit the service's Settings → Build Command directly, to be sure the new command is actually used.

**Two real production-only bugs hit and fixed while deploying (both were invisible in local dev because local `node_modules` already had stale/manually-built artifacts from earlier `npm run` calls — a truly clean environment is what exposed them):**
1. `be` build failed on Render with TS errors (`Parameter 'am' implicitly has an 'any' type`, `Property 'thumbnailKey' does not exist on type 'MediaPoint'`) because Prisma's generated client didn't exist yet — `npm install` does not reliably trigger `prisma generate` in this workspace layout. Fixed by adding `npm run -w be prisma:generate` before `npm run build -w be` in both `render.yaml` and the root `package.json`'s `build` script. Reproduced locally by deleting `node_modules/.prisma` + `node_modules/@prisma/client` before rebuilding, to confirm before pushing a fix blind.
2. `fe` build would fail the same way on a clean install (confirmed by building from inside `fe/` after deleting `packages/shared/dist`) — `next build`'s type-checking needs `packages/shared/dist/index.d.ts`, which doesn't exist unless something builds it first. Fixed by making `fe/package.json`'s own `build` script run `npm run build --prefix ../packages/shared` before `next build`, so it's self-contained regardless of which deploy platform's default commands run it.

The lesson embedded in both: **verify a fix against a genuinely clean state before declaring it done** (delete the generated artifact, don't just re-run the same command in an environment that already has it) — this repo's own dev history had already run `prisma generate` and both `tsc` builds multiple times, so `npm run build` looked fine locally right up until the first real clean-environment (Render/Vercel) deploy.
